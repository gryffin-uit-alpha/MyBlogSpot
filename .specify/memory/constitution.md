# BlogSpot Backend Constitution

## Core Principles

### I. Code Quality Standards

**MUST** adhere to the following code quality requirements:
- Go code MUST follow official Go coding conventions and pass `gofmt`, `go vet`, and `golint`
- All functions and exported types MUST have clear, concise documentation comments
- Cyclomatic complexity MUST NOT exceed 15 per function
- Code duplication MUST be eliminated through appropriate abstractions
- Database queries MUST use type-safe code generated by `sqlc` (no raw SQL strings in handlers)
- Error handling MUST be explicit and informative (wrap errors with context)
- Security vulnerabilities (SQL injection, XSS, command injection) MUST be prevented

**Rationale**: High code quality ensures maintainability, reduces bugs, and makes the codebase accessible to new contributors. Type-safe database queries prevent runtime errors and SQL injection attacks.

### II. Testing Standards (NON-NEGOTIABLE)

**MUST** follow test-driven development practices:
- Unit tests MUST be written before implementation (Red-Green-Refactor cycle)
- Test coverage MUST be ≥80% for all new code (handlers, database queries, utilities)
- Integration tests MUST cover:
  - Database migrations and schema changes
  - API endpoint contracts (request/response validation)
  - Authentication and authorization flows
  - Error handling and edge cases
- Tests MUST use real PostgreSQL database (not mocks) for integration tests
- All tests MUST pass before code review approval
- Performance-critical paths MUST include benchmark tests

**Rationale**: TDD ensures correctness from the start, prevents regressions, and serves as living documentation. Real database testing catches migration issues and query performance problems before production.

### III. User Experience Consistency

**MUST** maintain consistent API interfaces and user interactions:
- API responses MUST follow a standardized JSON structure:
  ```json
  {
    "success": boolean,
    "data": object|array,
    "error": { "code": string, "message": string }
  }
  ```
- HTTP status codes MUST be semantically correct (200, 201, 400, 401, 403, 404, 500)
- Error messages MUST be user-friendly and actionable (avoid exposing internal details)
- API versioning MUST follow `/api/v{MAJOR}/` URL pattern
- Breaking changes MUST be documented and communicated with migration guides
- Request/response schemas MUST be validated and documented (OpenAPI/Swagger)

**Rationale**: Consistent APIs reduce integration friction, improve developer experience, and make the system predictable and reliable for frontend teams and third-party consumers.

### IV. Performance Requirements

**MUST** meet the following performance standards:
- API response time MUST be <200ms for p95 under normal load
- Database queries MUST use proper indexes (monitored via `EXPLAIN ANALYZE`)
- N+1 query problems MUST be prevented (use joins or batch loading)
- Pagination MUST be implemented for list endpoints (default 50, max 100 items)
- Connection pooling MUST be configured appropriately for PostgreSQL
- Memory allocations MUST be minimized in hot paths (avoid unnecessary copies)
- Benchmark tests MUST be run for performance-critical code paths

**Rationale**: Performance is a feature. Slow systems frustrate users and waste resources. Proactive performance engineering prevents technical debt and scaling issues.

## Security Requirements

**MUST** follow security best practices:
- Passwords MUST be hashed using bcrypt (cost factor ≥12)
- Authentication tokens MUST be cryptographically secure and time-limited
- Input validation MUST be performed on all user-supplied data
- SQL injection MUST be prevented (use `sqlc` parameterized queries only)
- Secrets and credentials MUST NEVER be committed to version control
- HTTPS MUST be enforced in production environments
- Rate limiting MUST be implemented on authentication endpoints

**Rationale**: Security vulnerabilities expose users to risk and can result in data breaches, legal liability, and loss of trust.

## Development Workflow

**MUST** follow this workflow:
1. **Specification Phase**: Define requirements, API contracts, and acceptance criteria
2. **Test Phase**: Write failing tests that validate requirements
3. **Implementation Phase**: Write minimal code to pass tests
4. **Review Phase**: Code review ensures compliance with constitution principles
5. **Integration Phase**: Verify integration tests pass with real database
6. **Documentation Phase**: Update API docs, README, and migration guides

**Quality Gates**:
- All tests MUST pass (`go test ./...`)
- Code coverage MUST meet ≥80% threshold
- Linting MUST pass (`golint`, `go vet`)
- Database migrations MUST be reversible (down migrations included)
- Breaking changes MUST be approved by tech lead

**Rationale**: A structured workflow ensures quality at each stage, prevents shortcuts, and maintains consistency across the team.

## Governance

This constitution supersedes all other development practices. All code changes MUST comply with these principles.

**Amendment Process**:
- Proposed amendments MUST be documented with rationale
- Amendments MUST be approved by majority of core contributors
- Breaking principle changes require version MAJOR bump
- New principles or expanded guidance require version MINOR bump
- Clarifications and fixes require version PATCH bump

**Compliance Review**:
- All pull requests MUST be reviewed for constitutional compliance
- Non-compliance MUST be addressed before merge approval
- Complexity that violates simplicity principles MUST be justified in writing
- Performance regressions MUST be documented and approved
